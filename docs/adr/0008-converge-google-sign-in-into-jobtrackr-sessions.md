# Converge Google Sign-In into JobTrackr sessions

The OAuth route family runs through a dedicated session-aware Spring Security chain, while the rest of the API remains on its existing stateless JWT chain. The temporary OAuth session is invalidated on every success and failure path and never authenticates ordinary API requests.
Development and production use separate Google Cloud projects as well as separate Web OAuth clients. The External development project stays in Testing and requests only `openid email`; the External production project remains disabled until its exact hostname, consent-screen identity, support contact, homepage, and privacy-policy URL are ready for In production status.
Disabling Google after links exist is an emergency availability control: it preserves every Identity Link, leaves password sign-in working, and temporarily prevents Google-only Users from entering. Authentication throttles are temporary and never set persistent User locks. Callback responses prevent caching and referrer propagation, and callback query strings are excluded from application and reverse-proxy access logs. The feature deploys dark, is enabled and manually smoke-tested through the stable development tunnel, and is enabled in production only after the separate production project is ready; existing password Users require no backfill.
Authentication throttling uses Bucket4j core behind a JobTrackr-owned interface with bounded, expiring Caffeine storage and configurable policies for password login, registration, Google starts, and authenticated credential actions. Rejections use `RATE_LIMITED` with `Retry-After`; successful password login clears its email-and-IP failure bucket, and metrics carry only low-cardinality action and outcome labels.
Spring Security owns Google's OpenID Connect authorization-code flow, but a successful callback creates the same rotating refresh-cookie session used by password sign-in and redirects the browser to the SPA to bootstrap its in-memory access token. Google tokens are not persisted or exposed to React, and the temporary HTTP session used to validate the OAuth handshake is destroyed at completion. That session uses the host-only `JOBTRACKR_OAUTH_SESSION` cookie with a five-minute timeout, `/api/v1` path, `HttpOnly`, `SameSite=Lax`, and `Secure` in production. It is stored only in the running backend: a restart safely expires an in-flight flow, and multiple replicas require a shared Spring Session store before deployment. Google authentication is enabled explicitly and fails fast at startup when its backend-only client credentials or exact callback URI are absent; the frontend discovers availability from a public provider-capabilities endpoint. Development and production use separate Google Web OAuth clients, with exact callback URIs configured independently from the SPA public origin. Supported development callbacks include localhost, full Compose, and the stable Cloudflare tunnel at `https://test.ricardoguzdev.com`; random quick-tunnel hostnames are not assumed to work. Cloudflare Access remains an independent outer deployment control and does not participate in JobTrackr identity semantics. Sign-in and linking explicitly request Google's account chooser, while a Google-only User's password-creation flow additionally requests immediate reauthentication and an essential `auth_time`; it issues the five-minute single-use grant only when `auth_time` is no more than five minutes old and `sub` matches the existing Identity, failing closed if Google omits or returns stale evidence. Link and password-creation callbacks also require a still-valid JobTrackr refresh cookie belonging to the User stored in the temporary session, and ordinary Google sign-in cannot replace an already authenticated User session. Starting a new OAuth purpose replaces any one already pending in that browser; the superseded callback fails as expired or replaced and never reconstructs the previous purpose. Callback failures return only allowlisted result codes to the appropriate login or Account Settings route; raw provider errors, claims, emails, subjects, and authorization codes never enter application URLs. Basic application-level throttling covers the complete registration, sign-in, intent, and credential-mutation surface while valid callbacks rely on their one-time protocol state. Structured security logs record only the event, outcome, purpose, known User ID, and request correlation ID; durable audit history is out of scope. This preserves one application-session boundary while still using the provider's supported server flow.
